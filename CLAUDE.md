# CS602 Group Project: CVRP Solver

Group project for CS602 Algorithm Design and Implementation (SMU, AY2026/27 August Term).
Full spec: `docs/grp_proj_spec.pdf`. Step-by-step plan: `docs/CVRP_Project_Playbook.docx`.

## The problem

Capacitated Vehicle Routing Problem (CVRP). Given a depot (vertex 0), customers with demands,
a symmetric distance matrix and identical vehicles with one shared capacity, find routes that
minimise total distance.

A solution is FEASIBLE only if ALL of these hold:

1. Every route starts and ends at vertex 0, with no 0 inside a route.
2. Every customer 1..n appears exactly once across all routes.
3. Total demand on each route <= capacity.
4. Number of non-empty routes <= number of vehicles.

An infeasible output scores 0. Never print one.

## Input format

```
0 2 2 3              <- demands, index 0 = depot, always 0
0 2.5 5.6 6.0        <- (n+1) x (n+1) symmetric distance matrix, space separated
2.5 0 3.9 6.5
5.6 3.9 0 5.2
6.0 6.5 5.2 0
Capacity: 5
Vehicles: 2
```

Parse `Capacity:` and `Vehicles:` by keyword, not by line position. Tolerate extra spaces,
tabs, blank lines and CRLF line endings, because other groups' files may differ.

## Output format

```
21.8                 <- total cost (recomputed from the matrix right before printing)
0 1 0                <- one route per line
0 2 3 0
```

Skip empty routes. Print the cost with enough decimals to match the grader's recomputation.

## Time limits and scoring

| Size   | Limit L | Hard cut-off 1.5 L (score drops to 0.25) | Weight |
|--------|---------|------------------------------------------|--------|
| Small  | 30 s    | 45 s                                     | 10%    |
| Medium | 60 s    | 90 s                                     | 30%    |
| Large  | 180 s   | 270 s                                    | 60%    |

Per instance: `score = 1 / (0.5 * (2**max(0, t/L - 1) + c/b))`
where t = run time, c = our cost, b = best cost among all teams.
Every team's solver runs on instances generated by ALL groups.

## Solver design (implemented)

1. Construction (`cvrp/construct.py`): Clarke-Wright Savings (neighbour pairs only when
   n > 800) and Nearest Neighbor, keep the cheaper feasible one.
2. Vehicle-limit repair if routes > vehicles. If that fails: route elimination
   (`cvrp/fleet.py`, load consolidation plus an ejection pool), then a packing fallback
   (`bin_packing_routes`: distance-aware packing, then First-Fit-Decreasing variants).
3. Local search (`cvrp/local_search.py`): relocate, Or-opt, swap, 2-opt and two 2-opt* moves
   between each customer and its 30 nearest neighbours, all with delta evaluation. The
   `Solution` class keeps route_of, pos, prefix loads, prev and next so each check is O(1).
4. Metaheuristic (`cvrp/alns.py`): ALNS with random, worst, string (SISR style) and route
   removal, greedy insertion with blinks and regret-2 insertion, local search on changed
   routes, simulated annealing acceptance, adaptive operator weights. Settings are module
   constants (tuned on CVRPLIB X instances at 30 s).
5. Stop at 85% of L (clock starts at program start, including file reading). Every solution is
   validated before it is kept, and the best feasible one is printed even if an error occurs.

Benchmark at 30 s on 11 CVRPLIB X instances (n = 100 to 1000): all feasible, average gap to the
best known cost about 1.3% (0% to 4%, larger n has larger gap).

Until the instructor confirms that full VRP solver libraries are acceptable, OR-Tools and PyVRP
are used ONLY as benchmarks for analysis, never inside the submitted solver.

- Instance size classes (confirmed by the instructor): set by the group that makes the instance,

  Without it the solver assumes 30 s, because running late on a small instance costs far more
  than stopping early on a large one. The solver stops at 85% of L.

Keep this list in sync with the scripts whenever an argument is added or renamed.

## Coding rules

- External libraries are allowed, but add one only when it brings a clear gain (for example
  NumPy or Numba to speed up hot loops). List it with a pinned version in `requirements.txt`.
  Notebooks may also use matplotlib or pandas for analysis.
- Keep Python code simple and readable (plain lists, loops, small functions).
- Python is slow, so speed matters for large instances: use delta evaluation, neighbour lists
  and profiling before adding complexity. If Numba is used, enable `cache=True` because compile
  time counts toward the time limit.
- Every random process takes a seed. Same seed must give the same result.
- No hard-coded absolute paths. No debug prints to stdout in the solver (use stderr).
- After any change to solver logic, run the validator on the small and medium test instances.
- Measure timing from the command line with the batch runner, never in a notebook.
- Generator must guarantee feasibility: no demand above capacity, and the vehicle count at or
  above a First-Fit-Decreasing bin-packing bound.

## Working with Claude

## Golden rules

1. Never print an infeasible solution. Validate before output.
2. Never run past the time limit. Leave a safety margin for a slower grading machine.
3. Always keep the best feasible solution found so far and print it even if something fails.
4. Focus effort on large instances (60% of the score).
5. Our instances also grade other teams. Make them hard but always solvable.
6. Keep every experiment reproducible: command, seed, version, result.
